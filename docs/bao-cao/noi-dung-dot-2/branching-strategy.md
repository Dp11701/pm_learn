## branching-strategy

- Kiểm parser: Branching strategy (chu-de) · Đủ khối 9/9
- Nguồn đã mở: [Patterns for Managing Source Code Branches — Martin Fowler](https://martinfowler.com/articles/branching-patterns.html); [Capabilities: Trunk-based development — DORA](https://dora.dev/capabilities/trunk-based-development/); [A successful Git branching model (ghi chú 05/03/2020) — Vincent Driessen](https://nvie.com/posts/a-successful-git-branching-model/); [Git branching guidance (Azure Repos) — Microsoft Learn](https://learn.microsoft.com/en-us/azure/devops/repos/git/git-branching-guidance); [GitHub flow — GitHub Docs](https://docs.github.com/en/get-started/using-github/github-flow)
- Agent soát đã sửa:
  - Hotfix branch: câu cũ "Fowler xem hotfix branch là một lần đi lệch khỏi quy trình bình thường" → "Fowler nhận xét hotfix branch thường có nghĩa là đi lệch khỏi quy trình bình thường". Fowler viết ý này trong phần GitHub flow và có chữ "usually" ("thường"). Ở phần Hotfix Branch, ông còn nói nhóm làm Continuous Delivery có thể xử lý hotfix như mọi release bình thường.
  - So sánh, ô "Release và sửa lỗi" của trunk-based development: câu cũ "sửa bằng bản mới, hoặc cắt release branch ngắn hạn khi cần" → "Release thẳng từ trunk, bản sửa cũng đi qua trunk; hoặc cắt release branch khi cần". Chữ "ngắn hạn" chỉ có ở trunkbaseddevelopment.com, mà trang này không nằm trong Tham khảo. Fowler chỉ nói nhóm có thể chọn "branch for release" hoặc "release from trunk", và nhóm làm CD có thể release hotfix thẳng từ mainline.
- **Nên tự kiểm lại:**
  - Các ý đã khớp nguồn. Fowler: release branch chỉ nhận commit để ổn định bản sắp release, dễ quên đưa bản sửa về mainline, có người sửa trên mainline trước rồi cherry-pick; Git-flow vốn làm cho phần mềm có nhiều phiên bản cùng chạy (như phần mềm cài tại khách hàng); GitHub flow sửa lỗi production như mọi tính năng; nên hỏi vì sao merge rối thay vì cho qua. DORA: merge vào trunk ít nhất mỗi ngày, không quá ba nhánh đang hoạt động, không code freeze, review đồng bộ, bốn chỉ số theo dõi. Microsoft: main phải qua test, build sạch và luôn cập nhật; mỗi release branch đang hoạt động là thêm một phiên bản phải hỗ trợ; hai cách đưa bản sửa về main.
  - Ô "Nhánh phụ" của trunk-based development ghép hai nguồn. Cách chia nhóm nhỏ commit thẳng / nhóm lớn dùng nhánh ngắn là của Fowler, và ông nói nhánh ngắn là "không quá vài ngày". Mốc "merge ít nhất mỗi ngày" là của DORA, chặt hơn mốc của Fowler.
  - Ô "Hợp với: … dùng feature flag" của trunk-based development và cả hàng "Rủi ro chính" là nhận định của người viết. Trang DORA không nhắc feature flag. Fowler bàn feature flag trong phần continuous integration, còn Microsoft khuyên dùng feature flag khi có nhánh sống lâu.
  - Quy ước tên nhánh: Microsoft hiện gợi ý dạng feature/, bugfix/, hotfix/, users/…, và lấy release/20 làm ví dụ cho release branch. Tài liệu công cụ hay đổi nên bạn hãy xem lại. GitHub hiện có thêm ruleset bên cạnh branch protection.
  - Các con số trong bài như "merge trong một hai ngày", "một người duyệt", "3–4 ngày ghép code" chỉ là ví dụ giả định hoặc gợi ý thực hành, không phải chuẩn của nguồn nào. Microsoft nói hai reviewer là số tối ưu, theo một nghiên cứu họ dẫn.
  - Câu hỏi 5 (mỗi khách hàng một nhánh) khớp phần kết bài của Fowler: chép code ra rồi sửa riêng làm bản sao ngày càng khó nhận bản sửa từ gốc. Còn gợi ý dùng cấu hình hoặc feature flag và tính chi phí vào hợp đồng là của người viết.
