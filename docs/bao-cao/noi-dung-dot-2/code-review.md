## code-review

- Kiểm parser: Code review (chu-de) · Đủ khối 9/9
- Nguồn đã mở: [Code Review Developer Guide (Introduction, The Standard of Code Review, What to look for, Speed of Code Reviews, How to write code review comments, Small CLs) và trang Terminology — Google Engineering Practices](https://google.github.io/eng-practices/review/); [Capabilities: Streamlining change approval — DORA](https://dora.dev/capabilities/streamlining-change-approval/); [About pull request reviews — GitHub Docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews); [About protected branches — GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); [Expectations, Outcomes, and Challenges of Modern Code Review (ICSE 2013) — Alberto Bacchelli, Christian Bird, Microsoft Research](https://www.microsoft.com/en-us/research/publication/expectations-outcomes-and-challenges-of-modern-code-review/)
- Agent soát đã sửa:
  - Khái niệm Code health: câu cũ "dễ hiểu, dễ sửa, ít lỗi" → "dễ đọc, dễ hiểu, dễ bảo trì". Trang The Standard of Code Review không định nghĩa code health. Trang này chỉ nói thay đổi nên làm hệ thống dễ bảo trì, dễ đọc, dễ hiểu hơn (maintainability, readability, understandability). Trang không nhắc "ít lỗi".
  - Tự kiểm tra, câu 2: câu cũ "nếu chưa chia được thì reviewer ít nhất phải xét thiết kế tổng thể trước khi duyệt" → "nếu chưa chia được và reviewer không đủ thời gian xem hết, thì ít nhất góp ý về thiết kế tổng thể rồi trả lại tác giả sửa, chứ không approve cho qua". Trang Speed of Code Reviews khuyên viết vài góp ý về thiết kế tổng thể rồi gửi lại cho tác giả cải thiện, chứ không bảo xem thiết kế rồi duyệt.
  - Tự kiểm tra, câu 5: câu cũ "điều style guide không nói thì là sở thích cá nhân và nên theo cách code hiện có" → "điểm style mà style guide không nói là sở thích cá nhân, nên theo cách code hiện có, chưa có tiền lệ thì theo cách của tác giả". Câu mới thêm ý: tổ chức code mà thực chất là thiết kế thì xét theo nguyên lý kỹ thuật, không theo sở thích. Cả hai ý theo trang The Standard of Code Review. Câu hỏi có nhắc "tổ chức thư mục", mà Google coi thiết kế hầu như không bao giờ chỉ là chuyện style.
- **Nên tự kiểm lại:**
  - Các ý đã khớp nguồn. Google: approve khi thay đổi chắc chắn làm code health tổng thể tốt lên; câu trích "perfect" code đúng nguyên văn; mốc 100 dòng thường hợp lý, 1000 dòng thường quá lớn; lợi ích của thay đổi nhỏ; phản hồi tối đa một ngày làm việc; reviewer bận thì báo khi nào sẽ xem hoặc gợi ý người khác; ba nhãn "Nit:", "Optional:", "FYI:" (Google ghi "Optional (or Consider):"); leo thang lên Technical Lead khi bất đồng; CL là "changelist" (trang Terminology). GitHub: ba lựa chọn Comment, Approve, Request changes; số approval bắt buộc; huỷ approval cũ khi commit mới làm đổi diff; bắt buộc code owner duyệt. Bacchelli và Bird: tìm lỗi là động lực chính, nhưng kết quả ít xoay quanh lỗi hơn kỳ vọng.
  - DORA khớp các ý: peer review kèm tự động hoá là cách duyệt tốt nhất; duyệt từ ngoài nhóm ảnh hưởng xấu tới hiệu quả giao phần mềm và không có bằng chứng làm giảm change fail rate; dễ dẫn tới release đợt lớn, thưa hơn và rủi ro cao hơn; segregation of duties; CAB chuyển sang lo điều phối và các đánh đổi kinh doanh lớn. Có ba ô trong bảng So sánh là mô tả của người viết, trang DORA không nói: hàng "Bằng chứng" của CAB ("biên bản hoặc phiếu duyệt riêng"), ô "Khi nào", và câu mở đầu "khi xảy ra sự cố, tổ chức hay muốn thêm một tầng duyệt".
  - Câu "inspection nên dành cho phần rủi ro cao" lấy theo bài inspection đã có trong app. Lần soát này không mở lại ISTQB.
  - Đây là gợi ý thực hành của người viết, không có nguồn trực tiếp: đưa review vào Definition of Done và capacity, đưa formatter/linter vào CI để khỏi bàn style (trang What to look for không nhắc linter), danh sách thay đổi rủi ro cao, các tín hiệu theo dõi ở retro. Các con số trong Ví dụ thực tế cũng là giả định.
  - Tên gọi merge request (GitLab) và việc Bitbucket, Azure DevOps dùng pull request là kiến thức chung. Cả người viết lẫn agent soát đều không mở tài liệu của các hãng này. Thiết lập của GitHub có thể đổi theo thời gian, nên hãy xem lại trên công cụ nhóm bạn đang dùng.
